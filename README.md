# Сходим?

MVP чат-бота и мини-приложения в мессенджере MAX для держателей Пушкинской
карты (14–22 года). Помогает подобрать события, которые пользователь может
оплатить и на которые его пропустят по возрасту, и быстро собрать компанию
через карточки-приглашения.

## Как запустить локально

```bash
docker compose up -d          # поднимает PostgreSQL на localhost:5433

cd server
cp .env.example .env
npm install
npm run migrate               # применяет миграции (users, venues, events, invites, invite_responses)
npm run gen:events            # (опционально) перегенерировать тестовый срез событий
npm run seed                  # загружает тестовые события через дедупликацию
npm run dev                   # Fastify API на localhost:3000

cd ../miniapp
cp .env.example .env          # опционально: ключ Яндекс.Карт для "Время в пути"
npm install
npm run dev                   # Vite dev server, проксирует /api на localhost:3000
```

Тесты: `cd server && npm test` (vitest — дедупликация, подбор событий, онбординг).

## Тестовые данные

- `server/data/events.test.json` — 80 вымышленных событий по Москве (10 из
  них — намеренные почти-дубликаты для проверки дедупликации). Помечены как
  `"source": "тестовый срез"` с датой генерации в самом файле. Это НЕ реальная
  афиша.
- Перегенерировать: `npm run gen:events` (server).

## Переменные окружения (server/.env)

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `EVENT_SOURCE` | `kudago` (основной источник для MVP, бесплатный публичный API, без партнёрского ключа — см. ниже), `test` (тестовый JSON) или `proculture` (реальный API, нужен партнёрский ключ, которого нет) |
| `PRO_CULTURE_API_KEY` | ключ партнёра PRO.Культура.РФ. Плейсхолдер `[PRO_CULTURE_API_KEY]` — получить можно, договорившись о партнёрстве по e-mail с partners@team.culture.ru (шаблон письма: [docs/api-key-request-email.md](docs/api-key-request-email.md)). Ключ передаётся в каждом запросе параметром `apiKey`; после прекращения партнёрства API отвечает 403 |
| `PRO_CULTURE_API_BASE_URL`, `PRO_CULTURE_EVENTS_PATH` | адрес API и путь к афише — уточняются в документации, которую присылают вместе с ключом |

| `BOT_ADAPTER` | `mock` (адаптер в памяти для разработки) или `max` |
| `MAX_BOT_TOKEN` | токен бота MAX. Плейсхолдер `[MAX_BOT_TOKEN]` |

### Почему KudaGo, а не PRO.Культура.РФ

Партнёрский ключ PRO.Культура.РФ так и не получен (письмо-заявка в
[docs/api-key-request-email.md](docs/api-key-request-email.md) не отправлено
— решение пользователя), поэтому `ProCultureSource` остаётся нерабочим
каркасом. Основной источник для MVP — [KudaGoSource](server/src/sources/KudaGoSource.ts),
бесплатный публичный API [kudago.com/public-api](https://kudago.com/public-api/),
партнёрский ключ не нужен. Реализует тот же интерфейс `EventSource`, так что
`ProCultureSource` можно подключить позже без изменения остального кода —
просто сменой `EVENT_SOURCE`.

**Важно:** из моей среды разработки `kudago.com` физически недоступен —
DNS резолвится, но TCP-соединение виснет по таймауту (проверено `curl -v`;
другие внешние сайты, включая российские — mos.ru, yandex.ru, vk.com —
открываются нормально, так что это не блокировка по региону, а что-то
специфичное для их сервера/сети из моей песочницы). Поэтому `KudaGoSource`
не проверен вживую с реальными данными — только typecheck. Проверьте сами:
`EVENT_SOURCE=kudago` в `.env`, затем `npm run seed`.

Чтобы переключение источника на Render не могло уронить сервер (сид
запускается при каждом старте, в т.ч. при пробуждении бесплатного инстанса
из сна) — если живой источник недоступен, `npm run seed` не падает, а
откатывается на встроенные тестовые данные с предупреждением в лог
(`server/src/db/seed.ts`, `fetchWithFallback`).

## Время в пути и «Успею и вернусь» — офлайн-оценка, не Яндекс.Routing

И кнопка «Время в пути» на карточке события, и фильтр «Успею и вернусь»
считают время в пути офлайн: расстояние по прямой (haversine) делённое на
среднюю скорость 22 км/ч, без обращения к внешнему API на каждый клик
(`miniapp/src/travelEstimate.ts`). Причины две:

- Реальный `ymaps.route()` (Яндекс.Routing) для текущего ключа возвращает
  пустую ошибку `scriptError` при вызове — похоже, ключ не подключён к этому
  продукту (JS API для отображения карты и API маршрутизации — разные
  продукты Яндекса с разным доступом).
- Даже если бы работал: бесплатный лимит JS API — 100 запросов в сутки, а
  «Успею и вернусь» пересчитывается на каждое изменение фильтра по всем
  событиям — реальный маршрут сжёг бы лимит за один экран.

`VITE_YANDEX_MAPS_API_KEY` (`miniapp/.env`) при этом всё ещё нужен — но
только для отображения самой карты (`EventMap.tsx`), не для «Время в пути».
Без ключа карта скрывается, кнопка «Время в пути» продолжает работать.

## Фильтр «Радиус» вместо района/метро

Первая версия фильтра по местоположению определяла один из 12
административных округов Москвы по ближайшему центроиду — эта версия
убрана: она работала только для Москвы, и границы округов не давали
пользователю точного контроля («мне важны 3 км от дома», а не весь округ).
«Станция метро» имеет тот же изъян многогородности — справочник станций
пришлось бы вести отдельно на каждый город, а у KudaGo это поле есть не для
всех событий, у тестовых данных и PRO.Культура.РФ его не будет вовсе.

Вместо этого — `RadiusFilter` (`miniapp/src/components/RadiusFilter.tsx`):
пользователь включает «Рядом со мной» (геолокация браузера), двигает ползунок
1–30 км, круг радиуса рисуется прямо на карте (`EventMap.tsx`, `ymaps.Circle`).
Работает по чистой геометрии (haversine, `travelEstimate.ts`) — одинаково в
Москве, Казани или любом другом городе, без справочника округов/станций на
конкретный город. Полностью клиентский фильтр, как и «Успею и вернусь» —
никакого обращения к серверу или внешнему геокодеру на каждое движение
ползунка.

`ProCultureSource.mapResponseToRawEvents` и весь `MaxBotAdapter` — каркасы,
которые бросают понятную ошибку с описанием, что нужно доделать, когда придут
реальные ключ и документация. Остальной код (модель данных, дедупликация,
подбор, онбординг, мини-приложение) работает поверх `TestJsonSource` и
`MockMaxAdapter` без сторонних ключей.

## Реализовано (Must)

- Модель данных: `users`, `venues`, `events`, `invites`, `invite_responses`.
- Онбординг бота из трёх вопросов (остаток / кино-лимит / возраст),
  исправление через `/profile`.
- API подборки: фильтры по остатку, кино-лимиту, возрасту, дате, времени
  суток (`afterHour`/`beforeHour`, произвольный диапазон «с»–«до», не только
  фиксированное «после 18:00»), категориям (`categories` — можно выбрать
  «только театр», «без кино» и любую другую комбинацию), возрастному цензу
  события (`maxAge`, независимо от возраста самого пользователя). Пустой
  строгий результат отдаёт ближайшую альтернативу вместо пустого списка
  (`fallback: true`).
- Мини-приложение: карточки событий с фильтрами, кнопки «Отправить» /
  «Купить» (внешняя ссылка-заглушка) / «Купил» (уменьшает показываемый
  остаток). Переключатель Список/Карта — площадки показаны пинами на карте
  (OpenStreetMap, форма и цвет пина + иконка = категория события: плёнка —
  кино, маска — театр, нота — концерт, колонны — музей, рамка — выставка),
  тап открывает ту же карточку с действиями.
- Раздел «Зовут»: входящие приглашения одним списком, точная сумма нехватки
  («не хватает 700 ₽»), если событие не влезает в остаток получателя, три
  кнопки ответа, статус виден всем участникам.
- Отправка приглашения — с выбором получателя из списка контактов, знакомых
  боту (`RecipientPickerModal`), не «в никуда».
- Дедупликация событий: нормализация + нечёткое сравнение названий (~90%
  схожести, свой Левенштейн) + близость площадки (≤150 м) + окно по времени
  (≤15 минут) — пороги по §6.3 ТЗ.
- Дисклеймер о неофициальном статусе сервиса — в первом сообщении бота и
  внизу мини-приложения.

## Реализовано (Should)

- Источники событий вынесены за интерфейс `EventSource` — `TestJsonSource` и
  `ProCultureSource` взаимозаменяемы через `EVENT_SOURCE`.
- Адаптер бота вынесен за интерфейс `MessengerAdapter` — `MockMaxAdapter` и
  каркас `MaxBotAdapter` с одним контрактом.

## Сознательно не реализовано

- **Реальная интеграция с MAX Bot API и PRO.Культура.РФ** — нет ключей/токена
  и точного формата ответов API. Адаптеры готовы к подключению, входные точки
  явно бросают ошибку с указанием, что доделать.
- **Приём платежей** — вне разрешённого функционала. «Купить» — только
  внешняя ссылка, «Купил» — не финансовая операция, просто уменьшает
  показываемый остаток.
- **ФИО, телефон, паспортные данные** — не собираются и не хранятся; возраст
  хранится как группа (`14-15`/`16-17`/`18-22`), не дата рождения.
- **Парсинг сторонних афиш** (например, Яндекс.Афиши) — не реализован.
- **Геолокация друзей в реальном времени** — не реализована. Для «Время в
  пути» геолокация запрашивается разово через браузер, не отслеживается.

## Пробелы против `docs/skhodim_tz.md` (полное ТЗ появилось позже разработки)

- **Бот не подключён к живому серверу и БД.** `onboarding.ts` и
  `MockMaxAdapter` покрыты юнит-тестами, но не подняты как часть Fastify-
  процесса — таблица `users` заполняется только сидом для разработки.
- **Возраст хранится диапазоном (14-15/16-17/18-22), а не точным числом.**
  ТЗ §3.2/§6.2 сравнивает возрастной ценз события с точным возрастом
  пользователя — у меня сравнение грубее, через минимум диапазона.
- **Нет фильтра по абсолютной цене** (§3.2) — только по остатку (бюджету).
  По станции метро/району — нет буквально этих справочников, но есть
  функционально более гибкая замена: фильтр «Радиус» (см. выше), который
  дополнительно работает не только для Москвы.
- **Нет статуса события** `active/stale/removed` и правила «требует проверки
  после двух пропусков подряд» (§4).
- **Нет слияния нескольких источников с приоритетом PRO.Культура.РФ** (§6.3)
  — активен всегда только один источник за раз.
- **3.5 Напоминания, 3.6 День похода, 3.7 Итоги** (Should/Could) — не
  реализованы, ожидаемо для этого этапа.
